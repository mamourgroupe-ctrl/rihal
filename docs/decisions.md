- **السبب:** المشروع يستخدم `pnpm-lock.yaml` في جذر workspace؛ أدوات GitHub المدمجة لا تحتاج خدمة إضافية، وسير تدقيق مستقل لا يعتمد على نجاح توليد Prisma أو البناء.
- **المراجعة:** لا تُدمج تحديثات Dependabot تلقائيًا؛ تبقى تغييرات التبعيات خاضعة لمراجعة CI.

- **القرار:** فرض `fast-uri@3.1.9` عبر `pnpm.overrides`.
- **السبب:** كشف التدقيق الكامل قبل التعديل أربعة تنبيهات (2 متوسطة و2 منخفضة) على الإصدار `3.1.8` في تبعيات أدوات التطوير؛ أوصت قاعدة advisories بالإصدار `3.1.9` أو أحدث، وهو ضمن النطاق المتوافق مع المستهلكين الحاليين.

## 2026-10-27 — قاعدة البيانات وقواعد المجال

- **حدود المستأجر:** تستخدم علاقات `GroupMember` و`Document` و`Invoice` و`Notification` مفاتيح أجنبية مركبة تربط `tenantId` بالسجل الهدف. يتلقى كل service `tenantId` كقيمة سياق موثوقة منفصلة؛ لا يُضاف endpoint يقبلها من طلب المستخدم في هذه المرحلة.
- **المجموعات:** يُفرض حد الحجم داخل خدمة المجال مع قفل صف المجموعة، ويُدعّم بمشغّل PostgreSQL يمنع تجاوز الحد حتى عند الكتابة خارج الخدمة. يضمن فهرس جزئي قائدًا نشطًا واحدًا على الأكثر لكل مجموعة.
- **الفواتير:** لعدم وجود كيان عميل مستقل حاليًا، ترتبط الفاتورة اختياريًا بمعتمر وتحتفظ بلقطة اسم العميل؛ لم يُضف نموذج Customer جديد.
- **الأرشفة والوثائق:** تُستبدل عمليات الحذف بالأرشفة مع مفاتيح أجنبية `RESTRICT`. يُستخدم `storageKey` بدل رابط ملف، ولا تُفعّل إزالة نهائية آلية قبل اعتماد جدول احتفاظ قانوني؛ التفاصيل في `docs/data-retention.md`.
- **السجلات:** أُوقف تسجيل استعلامات Prisma في التطوير لأن معاملات SQL قد تحتوي أرقام جوازات أو بيانات وثائق.
- **البذور:** مستخدمو seed تجريبيون غير قابلين للمصادقة، وبياناتهم اصطناعية بوضوح؛ البذور ليست بيانات دخول أو إعداد إنتاج.

## 2026-10-27 — المصادقة والجلسات

- **تحديد الوكالة عند الدخول:** يقبل تسجيل الدخول `tenantSlug` وبريد المستخدم، لا `tenantId`. ذلك يحل تعارض البريد الفريد داخل كل وكالة؛ بعد الدخول، تؤخذ `tenantId` حصريًا من claims الرمز الموقّع، وتُرفض الحقول الإضافية في أجسام المصادقة.
- **الرموز والجلسات:** access JWT قصير العمر (15 دقيقة، HS256 مع issuer وaudience ثابتين)؛ refresh opaque عالي العشوائية، محفوظ بصيغة SHA-256 فقط، ويُدوّر عند الاستعمال. إعادة استعمال رمز مدوّر تلغي الجلسة كلها. تُراجع الجلسة والمستخدم والوكالة والدور في قاعدة البيانات عند كل طلب محمي لتطبيق الإلغاء فورًا.
- **تخزين refresh:** يُرسل في cookie `HttpOnly; SameSite=Strict` بمسار المصادقة، لا في JSON. تبقى access token في جسم الاستجابة مع `Cache-Control: no-store`.
- **كلمات المرور والاستعادة:** يُستخدم bcryptjs بكلفة 12. رموز الاستعادة عشوائية لمرة واحدة؛ يخزن التجزئة فقط في جدول مستقل وتُلغى الجلسات عند تغيير كلمة المرور. يوضع الرمز في fragment (`#token=...`) لا في query حتى لا يُرسل تلقائيًا إلى خادم صفحة الاستعادة أو ضمن Referer. تُشفّر وصلة الاستعادة AES-256-GCM بمفتاح مشتق عبر HKDF من `AUTH_SECRET` قبل وضعها في إشعار البريد الصادر؛ لا تظهر في الاستجابة أو السجلات.
- **التحديد المعدلي:** `@nestjs/throttler` يفرض حدودًا أشد على الدخول والاستعادة وحدًا عامًا على API. التخزين الحالي داخل الذاكرة لكل عملية؛ عند تشغيل عدة replicas يلزم تخزين مشترك (مثل Redis) قبل الإنتاج.
- **الإعداد والتسليم:** `AUTH_SECRET` إلزامي بطول 32 محرفًا على الأقل؛ يتطلب الإنتاج `AUTH_URL` عبر HTTPS و`SMTP_URL` و`SMTP_FROM`، ويفرض STARTTLS على SMTP أو TLS ضمنيًا عبر SMTPS. يرسل Nodemailer رابط الاستعادة بعد حفظه مشفرًا في outbox؛ إذا تعذر الإرسال يبقى الإشعار `PENDING` مع سجل تشغيلي لا يحتوي عنوان البريد أو الرابط. لا توجد بعد آلية إعادة محاولة تلقائية لهذه الإشعارات.

## 2026-10-29 — عزل المستأجرين بأدوار PostgreSQL وRLS

- **الأدوار والملكية:** يستخدم API دور `rihal_app` غير مالك، بلا `SUPERUSER` أو `BYPASSRLS` أو `CREATEROLE` أو `CREATEDB`، مع منح قراءة محدودة على أعمدة سجل الوكالات وصلاحيات `SELECT/INSERT/UPDATE` فقط على جداول المجال. لا يملك دور التطبيق حذفًا فعليًا؛ تبقى الأرشفة هي المسار المدعوم. يملك `rihal_migrator` المخطط والجداول ويُستخدم للهجرات والبذور فقط؛ لا يرثه دور التطبيق. تُنشأ الأدوار أولًا بواسطة مسؤول قاعدة البيانات عبر `packages/database/prisma/roles-bootstrap.sql`، وتُمرر كلمات المرور من secret manager لا من المستودع.
- **تغطية RLS:** تُفرض `ENABLE` و`FORCE ROW LEVEL SECURITY` وسياسة `USING` و`WITH CHECK` على كل جدول يحمل `tenantId`: المستخدمون، المعتمرون، المجموعات، العضويات، الوثائق، الفواتير وبنودها، الإشعارات، الجلسات، رموز refresh، ورموز استعادة كلمة المرور. جداول tenant-independent مثل سجل `tenants` لا تحمل `tenantId`؛ يرى التطبيق فقط أعمدة `id/slug/status/archivedAt` اللازمة لتسجيل الدخول والتحقق.
- **سياق المعاملة:** يضع `PrismaService.withTenant` القيمة عبر `set_config('app.current_tenant_id', ..., true)`، أي محليًا للمعاملة، ويقارنها بسياق AsyncLocalStorage الذي يملؤه interceptor من claims بعد تحقق JWT. تستعمل المسارات العامة فقط هوية resolved من slug أو lookup محدود بتجزئة رمز سري؛ لا تُقبل `tenantId` من جسم الطلب. يجب وضع كل قراءة/كتابة مستقبلية لجداول tenant-scoped داخل هذا الغلاف.
- **رموز ما قبل المصادقة:** أُضيف `tenantId` إلى refresh tokens وربط مركب بالجلسة. يسمح RLS في lookup العام بقراءة صف واحد فقط عند تطابق تجزئة الرمز مع GUC محلي مؤقت (`app.refresh_token_hash` أو `app.password_reset_token_hash`)؛ جميع الكتابات تتطلب سياق المستأجر العادي.
- **حد الثقة:** إعداد GUC مخصص في PostgreSQL هو حد ثقة بين API وقاعدة البيانات؛ يستطيع أي عميل يحمل بيانات اعتماد `rihal_app` ضبط GUC بنفسه. لذلك لا يحمي RLS من سرقة بيانات اعتماد التطبيق أو تنفيذ SQL تعسفي بحق الاتصال، ويظل منع SQL injection وحماية الأسرار ومراجعة هوية tenant في التطبيق إلزاميًا. يوفر RLS طبقة دفاع إضافية ضد استعلامات ناقصة أو أخطاء عزل في كود API.
- **التشغيل:** `DATABASE_URL` للتطبيق و`DIRECT_URL` للهجرات يجب أن يستخدما الدورين المنفصلين. إذا كانت قاعدة قائمة تملك جداولها هوية أخرى، يلزم نقل ملكية المخطط/الجداول إلى `rihal_migrator` بصلاحية مسؤول قبل تطبيق الهجرة؛ لا تستخدم اتصال API أو دورًا مشتركًا كمالك.
